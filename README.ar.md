# مساعد فرز السير الذاتية بالذكاء الاصطناعي
**AI Recruitment Screening Assistant**

مساعد توظيف مدعوم بالذكاء الاصطناعي، مبني باستخدام Python، لمساعدة فرق الموارد البشرية على تنظيم طلبات التوظيف، واستخراج المعلومات المنظمة من السير الذاتية، وتحليل متطلبات الوظائف، ودعم عملية تقييم المرشحين بناءً على الأدلة المتاحة.

صُمّم النظام لمساعدة المراجعين البشريين، وليس لاتخاذ قرارات التوظيف النهائية بدلًا منهم.

## 1. نظرة عامة على المشروع

تستقبل فرق التوظيف أحيانًا أعدادًا كبيرة من السير الذاتية للوظيفة الواحدة. وقد تستغرق مراجعة كل طلب يدويًا وقتًا طويلًا، كما قد تجعل المقارنة بين المرشحين بصورة متسقة أكثر صعوبة.

يهدف مشروع **AI Recruitment Screening Assistant** إلى تبسيط هذه العملية من خلال الجمع بين معالجة البريد الإلكتروني والمستندات، ونماذج اللغة الكبيرة (LLMs)، والتشابه الدلالي (Semantic Similarity)، والمقارنة القائمة على القواعد (Rule-Based Comparison)، وواجهة مستخدم تتيح لفريق الموارد البشرية مراجعة النتائج.

سير العمل المستهدف هو:

**إنشاء وظيفة ← استخراج المتطلبات ← مراجعة الشروط الإلزامية ← جمع السير الذاتية ← استخراج معلومات المرشحين ← مطابقة المتطلبات ← تصفية المرشحين وترتيبهم ← المراجعة البشرية**

يتكون المشروع من مكونات منفصلة لمعالجة المستندات، وعمليات الذكاء الاصطناعي، وخدمات الواجهة الخلفية، وواجهة المستخدم.

## 2. أهداف المشروع

- تقليل الأعمال اليدوية المتكررة أثناء الفرز الأولي للسير الذاتية.
- استخراج معلومات منظمة من السير الذاتية والأوصاف الوظيفية.
- مقارنة مؤهلات المرشحين بمتطلبات كل وظيفة.
- تحديد المتطلبات التي لا تتوفر أدلة كافية على استيفائها.
- الفصل بين الشروط الإلزامية والمؤهلات المفضلة.
- تنظيم نتائج المرشحين لتسهيل مراجعتها من قِبل الموارد البشرية.
- توفير واجهة واضحة لمراجعة النتائج وتسجيل القرارات.
- إبقاء قرارات التوظيف النهائية تحت إشراف الإنسان.

## 5. إعداد المشروع

يستخدم المشروع Python وبيئة افتراضية (Virtual Environment) لعزل المكتبات والاعتماديات الخاصة به.

### المتطلبات الأساسية

- Python 3.
- Git.
- Visual Studio Code أو أي محرر آخر مناسب لبرمجة Python.
- بيانات اعتماد Gmail API، إذا كان تكامل Gmail مستخدمًا.
- مفتاح API من OpenRouter ونموذج مدعوم، إذا كان التنفيذ يعتمد على OpenRouter.
- مكتبات FastAPI وStreamlit إذا كانت هذه المكونات موجودة في النسخة المقدمة.

### إنشاء بيئة افتراضية

على macOS أو Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

على Windows:

```powershell
python -m venv .venv
.venv\Scripts\activate
```

تثبيت اعتماديات المشروع:

```bash
pip install -r requirements.txt
```

يجب أن يحتوي ملف `requirements.txt` على جميع المكتبات المطلوبة لتشغيل النسخة النهائية من المشروع.

## 6. التكامل مع Gmail

يهدف تكامل Gmail إلى استرجاع رسائل التوظيف وتحديد المرفقات التي تحتوي على السير الذاتية للمتقدمين.

يعتمد هذا التكامل على Gmail API وآلية التفويض OAuth 2.0.

تشمل خطوات الإعداد:

1. إنشاء مشروع في Google Cloud.
2. تفعيل Gmail API.
3. إعداد شاشة موافقة OAuth وبيانات الاعتماد.
4. تفويض التطبيق للوصول إلى حساب Gmail الخاص بالموارد البشرية.
5. استخدام صلاحية القراءة فقط عند الحاجة إلى قراءة الرسائل والمرفقات دون تعديلها.
6. استرجاع الرسائل ذات الصلة والبيانات الوصفية الخاصة بها.

يجب تخزين رموز OAuth محليًا وحمايتها من الوصول غير المصرح به.

كما ينبغي ألا يطلب التطبيق صلاحيات Gmail غير الضرورية أو يكشف بيانات الاعتماد داخل الكود المصدري.

## 7. معالجة البريد الإلكتروني ومرفقات السير الذاتية

تحدد مرحلة معالجة البريد الإلكتروني الرسائل المتعلقة بطلبات التوظيف، وتجهز المرفقات المدعومة لاستخراج النصوص منها.

تشمل العملية المستهدفة:

1. البحث عن رسائل التوظيف باستخدام عوامل البحث في Gmail.
2. قراءة معرّفات الرسائل والمرسلين والعناوين والبيانات الوصفية للمرفقات.
3. تحديد المرفقات بصيغتي PDF وDOCX.
4. تنزيل المرفقات المدعومة.
5. فك ترميز محتوى المرفقات عند الحاجة.
6. تجاوز الملفات غير المدعومة أو غير القابلة للاستخدام.
7. تتبّع معرّفات الرسائل التي تمت معالجتها لتقليل تكرار المعالجة.

ينبغي أن يتعامل التطبيق مع وجود عدة مرفقات في الرسالة الواحدة، وأن يواصل معالجة بقية الطلبات إذا فشلت معالجة أحد الملفات.

يعتمد مستوى الأتمتة الفعلي على ما نُفّذ في تكامل Gmail داخل النسخة المقدمة.

## 8. استخراج النصوص من السير الذاتية

يستخرج التطبيق النصوص من ملفات السير الذاتية المدعومة قبل تمرير محتواها إلى مرحلة معالجة الذكاء الاصطناعي.

### الصيغ المدعومة

- ملفات PDF باستخدام `pypdf`.
- ملفات DOCX باستخدام `python-docx`.

ينبغي أن تقوم مرحلة الاستخراج بما يلي:

- قراءة محتوى المستند.
- دمج النص المستخرج في سلسلة نصية موحدة.
- إزالة المسافات البيضاء غير الضرورية.
- اكتشاف المستندات الفارغة أو غير القابلة للقراءة.
- التعامل مع أخطاء الاستخراج.
- الاحتفاظ بالمعلومات المرتبطة بالمرشح والملف الأصلي.

قد تحتاج ملفات PDF الممسوحة ضوئيًا إلى تقنية التعرف الضوئي على الحروف (OCR)، لأن `pypdf` لا يتعرف تلقائيًا على النص الموجود داخل الصور فقط.

يصبح النص المستخرج مدخلًا لمرحلة استخراج معلومات المرشح.

## 9. تجهيز الوصف الوظيفي

يحدد الوصف الوظيفي المؤهلات والمتطلبات المرتبطة بالوظيفة.

يمكن للنظام استخدام ملف نصي أو بيانات منظمة لتمرير الوصف الوظيفي إلى مكوّن الذكاء الاصطناعي.

تشمل المعلومات المهمة:

- المسمى الوظيفي.
- المهارات التقنية المطلوبة.
- الخبرة المطلوبة.
- المؤهلات التعليمية.
- اللغات.
- الشهادات المهنية.
- الشروط الإلزامية.
- المؤهلات المفضلة.

ينبغي تنظيم المتطلبات المستخرجة في بنية موحدة حتى يمكن تقييم كل متطلب بصورة مستقلة.

كما ينبغي إتاحة الفرصة لفريق الموارد البشرية لمراجعة المتطلبات المستخرجة وتحديد الشروط الإلزامية قبل بدء فرز المرشحين.

## 10. استخراج المعلومات باستخدام الذكاء الاصطناعي

يحوّل مكوّن الذكاء الاصطناعي النصوص غير المنظمة إلى معلومات منظمة تستطيع بقية أجزاء التطبيق معالجتها.

### استخراج معلومات الوصف الوظيفي

يُطلب من النموذج تحديد:

- المسمى الوظيفي.
- المهارات المطلوبة.
- متطلبات الخبرة.
- متطلبات التعليم.
- اللغات.
- الشهادات المهنية.
- المؤهلات الإلزامية والمفضلة.

### استخراج معلومات المرشحين

يحلل النموذج نص السيرة الذاتية لاستخراج معلومات مثل:

- الاسم وبيانات الاتصال، عند توفرها.
- المهارات التقنية.
- الخبرات العملية.
- المؤهلات التعليمية.
- اللغات.
- الشهادات المهنية.

تُنظّم المعلومات الناتجة في بيانات JSON ذات بنية محددة.

يستخدم التطبيق نموذج ذكاء اصطناعي عبر تكامل API المُعدّ. وتعتمد جودة الاستخراج على النص المدخل والنموذج والتعليمات (Prompts) المستخدمة.

يجب ألا يفترض النظام أن المرشح يمتلك مهارة أو مؤهلًا لمجرد أن النموذج يعتقد أن ذلك محتمل. ينبغي تصنيف المعلومات المفقودة على أنها غير متوفرة أو تحتاج إلى مراجعة.

## 11. المطابقة الأولية بين السيرة الذاتية والوظيفة

يقارن مكوّن المطابقة المعلومات المستخرجة من المرشح بمتطلبات الوظيفة.

ينبغي تقييم كل متطلب بصورة مستقلة بدلًا من الاعتماد على درجة تشابه عامة واحدة فقط.

### المقارنة القائمة على القواعد (Rule-Based Comparison)

يمكن استخدام قواعد محددة للتحقق من المتطلبات الصريحة، مثل وجود شهادة مهنية محددة أو مؤهل موثق في السيرة الذاتية.

### التشابه الدلالي (Semantic Similarity)

عند تنفيذ هذه الميزة، تستخدم مكتبة Sentence Transformers لإنشاء تضمينات نصية (Embeddings) تمثل المعنى.

يمكن استخدام نموذج تضمين مثل:

`sentence-transformers/all-MiniLM-L6-v2`

لمقارنة متطلبات الوظيفة بالمعلومات ذات الصلة في السيرة الذاتية.

يقيس **Cosine Similarity** مدى التشابه بين متجهي التضمين.

يفيد التشابه الدلالي عندما يعبّر المرشح عن خبرة مناسبة بكلمات تختلف عن الكلمات المستخدمة في الوصف الوظيفي.

لكن التشابه الدلالي وحده لا يثبت استيفاء المتطلب. لذلك ينبغي الجمع بين نتائجه والمعلومات المنظمة والقواعد المناسبة والأدلة الداعمة.

### فئات المطابقة

الفئات المستهدفة هي:

- **مستوفٍ للمتطلب (Meets):** توجد أدلة كافية تدعم استيفاء المتطلب.
- **مستوفٍ جزئيًا (Partially Meets):** تدعم الأدلة جزءًا من المتطلب فقط.
- **غير مستوفٍ وفق الأدلة المتاحة (Does Not Meet):** لا تثبت الأدلة المتاحة استيفاء المتطلب.

ينبغي أن تتضمن النتائج أدلة ذات صلة من السيرة الذاتية كلما أمكن. كما يجب التمييز بين عدم توفر دليل على المؤهل وبين وجود دليل يؤكد غيابه.

## 12. تصفية المرشحين وترتيبهم

بعد تقييم متطلبات المرشحين، يمكن للنظام تنظيم النتائج لمساعدة فريق الموارد البشرية على تحديد أولوية مراجعة الطلبات.

### المتطلبات الإلزامية (Must-Have Requirements)

تُقيّم الشروط الإلزامية بصورة منفصلة عن المؤهلات المفضلة.

يمكن وضع المرشحين الذين لا يستوفون جميع الشروط الإلزامية في مجموعة منفصلة لمراجعتها بصورة إضافية.

ويجب أن يظل هؤلاء المرشحون متاحين للمراجعة البشرية، بدلًا من استبعادهم نهائيًا اعتمادًا على تقييم آلي وحده.

### ترتيب المرشحين (Candidate Ranking)

يمكن ترتيب المرشحين الذين يستوفون الشروط الإلزامية المحددة وفق نتائجهم في المتطلبات المفضلة والمؤهلات الأخرى ذات الصلة.

قد يعتمد منطق الترتيب على الجمع بين:

- نتائج مطابقة المتطلبات.
- المعلومات المنظمة عن المرشحين.
- عمليات التحقق القائمة على القواعد.
- قياسات التشابه الدلالي، عند تنفيذها.

ينبغي توثيق أوزان التقييم وإتاحة ضبطها عند الحاجة.

ولا يجوز تقديم درجة التشابه أو ترتيب المرشح على أنها احتمال لنجاحه في الوظيفة أو مقياس نهائي لقيمته المهنية.

### مخرجات الترتيب

تشمل المخرجات المستهدفة:

- معلومات المرشح.
- نتائج المطابقة.
- الدرجات المتاحة.
- فئات الترتيب.
- المتطلبات التي لم تثبت مطابقتها.
- الأدلة الداعمة.

الهدف من الترتيب هو مساعدة الموارد البشرية على تنظيم المراجعة، وليس أتمتة قرار التوظيف النهائي.

## 13. تنظيم النتائج وحفظها

ينظم التطبيق المعلومات المستخرجة ونتائج الفرز في بيانات منظمة يمكن للواجهة استرجاعها.

قد تشمل حقول البيانات:

- معلومات المرشح.
- مصدر الطلب أو معرّف رسالة البريد الإلكتروني.
- اسم ملف السيرة الذاتية.
- المهارات والمؤهلات المستخرجة.
- متطلبات الوظيفة.
- نتائج مطابقة كل متطلب.
- درجات الترتيب وفئاته.
- قرارات الموارد البشرية وملاحظاتها.

يُعد JSON مناسبًا لتبادل البيانات المنظمة والتخزين البسيط في النماذج الأولية. ويمكن استخدام قاعدة بيانات لتوفير استمرارية أفضل للبيانات مع توسع التطبيق.

ينبغي أن يتجنب التنفيذ إنشاء سجلات مكررة للمرشح، وأن يحافظ على العلاقة بين المرشح والوظيفة وطلب التوظيف الأصلي.

تعتمد آلية التخزين الفعلية على التنفيذ الحالي. فالسجلات المحفوظة في ذاكرة التطبيق والملفات بصيغة JSON وقواعد البيانات تختلف في مدى استمرارية البيانات، ولا ينبغي التعامل معها على أنها متكافئة.

## 14. الواجهة الخلفية وواجهة المستخدم

### 14.1 الواجهة الخلفية باستخدام FastAPI

توفر FastAPI واجهة HTTP API التي تربط واجهة المستخدم بمنطق التطبيق.

تتولى الواجهة الخلفية التحقق من صحة الطلبات، واستدعاء عمليات المعالجة المناسبة، وإرجاع استجابات منظمة.

بحسب نقاط الاتصال المنفذة، قد تشمل مسؤولياتها:

- استرجاع الوظائف المتاحة.
- إنشاء الأوصاف الوظيفية أو إدارتها.
- فرز نص السيرة الذاتية وفق وصف وظيفي.
- استرجاع سجلات المرشحين.
- استرجاع نتائج الفرز والترتيب.
- استرجاع قرارات الموارد البشرية المحفوظة.
- تحديث قرارات المرشحين وملاحظاتهم.

تحدد مخططات Pydantic بنية البيانات المتوقعة في الطلبات والاستجابات.

يُستخدم Uvicorn لتشغيل تطبيق FastAPI.

إذا كان اسم كائن التطبيق هو `app` داخل الملف `backend/main.py`، فيمكن تشغيل الواجهة الخلفية باستخدام:

```bash
uvicorn backend.main:app --reload
```

بعد ذلك، يمكن الوصول إلى توثيق API عبر:

```text
http://127.0.0.1:8000/docs
```

يجب أن يتوافق أمر التشغيل ونقاط الاتصال مع الملفات الموجودة فعليًا في المشروع.

### 14.2 واجهة المستخدم باستخدام Streamlit

توفر Streamlit واجهة المستخدم للتفاعل مع مساعد التوظيف.

تهدف الواجهة إلى تنظيم مهام التوظيف الأساسية في صفحات وأقسام واضحة وسهلة الاستخدام.

#### إدارة الوظائف

- إدخال المسمى الوظيفي والوصف الوظيفي.
- إنشاء وظيفة باستخدام وظائف الواجهة الخلفية المتاحة.
- استرجاع الوظائف المتاحة.
- مراجعة معلومات الوظيفة المستخدمة في الفرز.

#### فرز المرشحين

- عرض سجلات المرشحين المحفوظة.
- رفع سيرة ذاتية بصيغة PDF أو DOCX أو TXT للفرز الفردي، إذا كانت الميزة مدعومة.
- اختيار الوصف الوظيفي المناسب.
- إرسال نص السيرة الذاتية المستخرج إلى الواجهة الخلفية.
- عرض نتائج الفرز التي يعيدها النظام.

#### مراجعة المرشحين

- عرض أسماء المرشحين ومعلومات الاتصال المتاحة.
- إظهار الدرجات وفئات الترتيب المتاحة.
- مراجعة المؤهلات المستخرجة.
- فحص معلومات المطابقة والأدلة المفقودة.
- عرض اسم ملف السيرة الذاتية عند توفره.

#### قرارات الموارد البشرية

- اختيار مرشح.
- تسجيل القرار بإحدى القيم التالية: `Shortlist` أو `Review Later` أو `Reject`.
- إضافة ملاحظات للرجوع إليها لاحقًا.
- استرجاع القرارات السابقة عند دعم هذه الميزة.

تستخدم الواجهة مكتبة `requests` لإرسال طلبات HTTP إلى FastAPI، ومكتبة Pandas لتنظيم معلومات المرشحين في جداول.

### 14.3 التواصل بين الواجهة الأمامية والخلفية

يعتمد التطبيق على بنية العميل والخادم (Client-Server Architecture):

```text
مستخدم الموارد البشرية
        |
        v
واجهة Streamlit
        |
        | طلبات HTTP
        v
الواجهة الخلفية FastAPI
        |
        v
خدمات التطبيق
        |
        v
استخراج المعلومات / المطابقة / الترتيب
        |
        v
استجابة API منظمة
        |
        v
عرض النتائج في Streamlit
```

يسمح هذا الفصل بتطوير واجهة المستخدم ومنطق التطبيق واختبارهما بصورة مستقلة.

### 14.4 حدود التنفيذ الحالي

يجب أن تميز النسخة النهائية من المشروع بين الوظائف المنفذة فعليًا والوظائف المخطط لإضافتها.

بحسب الكود الحالي، قد تحتاج الجوانب التالية إلى استكمال التكامل:

- استكمال مسار معالجة رسائل Gmail تلقائيًا حتى الوصول إلى فرز المرشحين.
- حفظ سجلات الوظائف والمرشحين بصورة موثوقة.
- حفظ نتائج الفرز الفردي ضمن مجموعة المرشحين المصنفين.
- توفير نقطة اتصال لاسترجاع ملفات السير الذاتية الأصلية أو تنزيلها.
- ربط تصفية الشروط الإلزامية وترتيب المرشحين بواجهة المستخدم.
- إضافة اختبارات شاملة للواجهة الخلفية وسير العمل الكامل.

لا ينبغي وصف أي من هذه الوظائف بأنها مكتملة إلا بعد تنفيذها واختبارها.

## 15. إعدادات المشروع

أنشئ ملفًا محليًا باسم `.env` إذا كان التطبيق يقرأ الإعدادات من متغيرات البيئة.

```env
OPENROUTER_API_KEY=your_openrouter_api_key

```

استبدل القيم التجريبية ببيانات الاعتماد ومعرّف النموذج المطلوبين في التنفيذ.

قد تحتاج أيضًا إلى بيانات اعتماد OAuth الخاصة بـ Gmail، بحسب الإعدادات المستخدمة.

**لا ترفع مفاتيح API أو بيانات اعتماد OAuth أو رموز المصادقة أو السير الذاتية الخاصة أو أي معلومات حساسة إلى مستودع GitHub عام.**

يمكن استخدام ملف `.env.example` لتوضيح أسماء متغيرات البيئة المطلوبة دون تضمين أسرار حقيقية.

## 17. الاختبار

ينبغي اختبار المشروع باستخدام أوصاف وظيفية متنوعة وعينات مناسبة من السير الذاتية.

تشمل حالات الاختبار المهمة:

- ملفات PDF وDOCX صالحة.
- المستندات الفارغة أو التالفة.
- صيغ المرفقات غير المدعومة.
- المستندات التي لا تحتوي على نص قابل للاستخراج أو تحتوي على قدر ضئيل منه.
- نقص المعلومات المتعلقة بالمرشح.
- التعبير عن المتطلبات نفسها باستخدام صياغات مختلفة.
- المرشحون الذين لا تتوفر أدلة على استيفائهم للشروط الإلزامية.
- رسائل البريد الإلكتروني المكررة.
- طلبات API غير الصالحة.
- انقطاع الاتصال بالواجهة الخلفية.
- حفظ قرارات الموارد البشرية واسترجاعها.

يجب أن تتحقق الاختبارات من تعامل التطبيق مع الأخطاء بصورة آمنة، وأن تظل النتائج مفهومة للمراجعين البشريين.

## 18. القيود

- قد ينتج الذكاء الاصطناعي معلومات غير مكتملة أو غير صحيحة.
- لا يثبت التشابه الدلالي أن المرشح يستوفي مؤهلًا معينًا.
- قد تحتاج ملفات PDF الممسوحة ضوئيًا إلى تقنية OCR.
- قد تؤثر حصص Gmail API ومشكلات المصادقة في استرجاع الرسائل.
- تعتمد جودة الترتيب على المعايير المحددة ومنطق التقييم المستخدم.
- يتطلب التشغيل الآلي الكامل تكامل مكونات Gmail والاستخراج والمطابقة والترتيب والتخزين وواجهة المستخدم.
- يتطلب تنزيل السير الذاتية الأصلية دعمًا مناسبًا من الواجهة الخلفية.
- تحتاج المعلومات الحساسة للمرشحين إلى ضوابط مناسبة للتحكم في الوصول وحماية البيانات.

- يوفر أدلة داعمة لنتائج الفرز.
- يسمح للمراجعين البشريين بفحص التقييمات التي ينتجها الذكاء الاصطناعي ومراجعتها والاعتراض عليها.
